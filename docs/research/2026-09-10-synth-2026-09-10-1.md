## Findings

1. **The Bernstein pattern does not transfer directly.**  
   The pattern named in the line — “CI re-verifies the committed receipt on every push to main” — presumes an immutable, addressable revision such as a git commit. The receipt can be re-checked because both proof and target are anchored to the same commit-shaped snapshot. In Hngh, the prior material frames the problem differently: proofs are produced against a **mutable, unversioned plan ledger**, so there is no durable “main commit” equivalent unless Hngh creates one.

2. **The Hngh failure mode is state drift, not classical proof rot.**  
   A proof published against ledger state `S₀` may remain internally valid for `S₀` while becoming misleading after sync advances the ledger to `S₁`. The danger is not that the proof bytes degrade; it is that consumers keep treating an `S₀`-bound proof as authoritative for `S₁`.

3. **The guardrail is therefore state-binding plus freshness adjudication.**  
   The concrete guardrail should be: bind every published proof to a canonical ledger checkpoint — epoch, root hash, sequence number, or equivalent — and make ledger sync/publish explicitly compare the proof’s checkpoint against the current checkpoint. If they differ, the proof is not allowed to remain silently “published”; it must be rejected from the current authoritative view, marked stale/superseded, or retained only with its validity window exposed.

4. **Mapping, restated:**
   - Bernstein-side analog: push to main → CI checks committed receipt against immutable tree.
   - Hngh-side analog: ledger sync/publish → gate checks proof artifact against ledger checkpoint identity.
   - Key substitution: **re-verify proof logic** becomes **verify state identity and validity interval**. Re-running proof logic may still be useful, but it is insufficient unless the ledger checkpoint is fixed.

5. **The minimal invariant:**  
   No proof may be presented as current unless `proof.ledger_checkpoint == current_authoritative_checkpoint`, or the consumer is explicitly shown that the proof is historical/superseded.

## Recommendations

1. **Introduce an addressable ledger checkpoint if one does not already exist.**  
   Prefer an append-only evidence/authority ledger model consistent with the prior-art pointers to `[[concepts/evidence-ledger]]`. At minimum, derive a canonical hash/root plus monotonic epoch for the plan ledger at each sync boundary. Do not rely on file mtimes, local timestamps, or rendered git dates; prior art already warns about timezone/local-time rendering fabricating missing commits.

2. **Bind proof artifacts to checkpoints.**  
   Every published proof artifact should carry: `ledger_id`, `ledger_epoch` or sequence, `ledger_root_hash`, canonicalization version, hash algorithm, proof generation time in UTC, and expiry/supersession semantics. Until exact modules are verified, treat paths such as `/home/bricker/Projects/etc/hngh/src/proof/artifact.rs` from prior material as **candidate locations only**, not confirmed files.

3. **Make sync/publish a gate, not a background copy.**  
   On ledger sync to the authoritative branch/view, compute the current checkpoint and evaluate all affected proofs:
   - match → remain published/current;
   - mismatch but older checkpoint still exists → retain as historical with explicit supersession;
   - checkpoint missing/unreconstructable → mark invalid/unverifiable and alert.

4. **Separate validity classes in storage and API.**  
   Use explicit states such as `current`, `stale`, `superseded`, `invalid`, `unverifiable`. Avoid boolean “valid” alone; it hides the difference between “proof logic failed” and “ledger moved.”

5. **Preserve historical proofs without letting them impersonate current ones.**  
   Keep old proof artifacts and their checkpoint bindings for auditability, but ensure default queries return only `current` proofs. Historical proofs should require an explicit `as_of` checkpoint query.

6. **Add race-focused tests.**  
   Test at least: proof published while sync is in flight; two writers racing adjacent ledger entries; sync completing after proof publication; checkpoint canonicalization stability across platforms/timezones; replay from an old checkpoint; consumer behavior when default query hides stale proofs.

7. **Operationalize drift as an observable event.**  
   Emit metrics/logs for `proof_state_transition`, checkpoint mismatches, rejected publishes, and stale-proof reads. A race that only appears in consumer confusion is still a live incident class.

- Decide whether the plan ledger becomes append-only/versioned, or remains mutable with a derived checkpoint manifest. Append-only is cleaner; derived checkpointing is less invasive but easier to get subtly wrong.
