# Why did alert identity repeat-crumbs ("identical breadcrumb loop detected") fire, and what disposition (fix or park) closes it?

Status: crystallized 2026-10-07 from routed plan 2026-09-15-routed-repeat-crumbs;
alert identity `repeat-crumbs`, filed by `automation/jobs/oversight-tick.sh`.

## Verdict

fixed (second application). The detector was a false-positive-only
machine and is now deleted from the refounded tree. The 2026-09-02 plan
already diagnosed and fixed the identical root cause in the standalone
hngh-automation repo (commit ca34ce6, probe + call site, 8 lines); that
fix was lost when the 2026-09-07 subtree merge (67372979, snapshot of
hngh-automation 3f1d5b4) carried the probe back in, and the old repo
then retired to the external operator archive. Genuinely stuck loops
remain covered by the steer leg's typed hazard gate (same file,
`steer_leg` / `ask_noul 'steer_hazard'`), which decides loop-ness over
the execution tail at every beat.

## Evidence

1. Render format makes cross-time detection impossible:
   `lib/crumbs-db.py render()` emits `"%s | %s | %s | %s" % (ts, job,
   event, detail)` — the timestamp is part of every line. The probe
   (`probe_repeated_breadcrumbs`, deleted this session) compared the
   last two exported lines for byte-identity. Two identical lines
   therefore necessarily carry the same second: the only reachable
   signal is same-second duplicate burst writes, never a loop spanning
   ticks (a real stuck loop writes the same crumb minutes apart; the
   timestamps differ, so the lines differ).

2. Burst writers produce the reachable signal. Live rows in
   `state/crumbs.db` today: 2026-09-15T15:32:17Z carries
   `ttsr-rule-drift:no-ungrounded-time-of-day` twice (rowids 84834/84835)
   and `ttsr-fit:threeinj` three times (84837-84839) — same job, event,
   and detail, same second, emitted by `cadence/calendar/daily/22-ttsr-fit.sh`
   `file_report` loops. Any oversight tick reading tail-2 inside such a
   burst fires REPEAT.

3. Firing history matches the burst mechanism. STATE.md has exactly two
   repeat-crumbs alert rows ever: 2026-09-10T22:50:02Z and
   2026-09-15T13:00:03Z. The 09-10 burst around the alert second shows
   `ttsr-fit:threeinj` written twice adjacent (STATE.md:2257 window) —
   the alert fired in the same second as a duplicate pair. The 09-15
   trigger rows are unrecoverable (crumbs.db rowid gap 83015-83422; the
   probe's `--tail 2` view is ts-ordered and the pair was pruned), but
   the 13:00 tick collided with the hourly 33-research-beat burst
   writer (its rows sit at 11:12/12:09 with identical bursts seen at
   15:32). No firing since 2026-09-15 (three weeks of silence at
   2026-10-07).

4. Prior art is the same conclusion: docs/project/plans/
   2026-09-02-routed-repeat-crumbs.plan.md (status=executed) — "false
   positive, detector deleted ... only reachable via same-second
   concurrent duplicates ... never a loop. A real stuck loop spans
   minutes → timestamps differ → probe blind to its actual target."
   Its fix ca34ce6 died with the subtree refoundation; the 09-10 routed
   plan went parked (identity re-occurred without landing), and the
   09-15 plan is this delve's carrier.

5. Redundancy: loop recognition over time is owned elsewhere —
   `steer_leg` runs the typed hazard Noul (`steer_hazard`: "repeated
   identical execution with no distinct progress") over the recent
   execution tail at every beat, and agent-stall probes cover stalled
   sessions. The 2-line crumb probe added no signal the plane lacks.

6. This session's fix: deleted `probe_repeated_breadcrumbs` + its call
   site and `repeat-crumbs` alert from
   `automation/jobs/oversight-tick.sh`; removed the `repeat-crumbs`
   digest pattern and docstring mention from
   `automation/scripts/notify-email.py`; dropped the identity from the
   README importance-rubric table. Verification: `bash -n` and
   `python3 -m py_compile` green, zero residual references; the next
   cadence tick is the live smoke.

## Adversarial check

- "Deleting the probe loses stuck-loop detection." The probe could
  never fire on a cross-time loop (evidence 1): deleting it removes
  only a same-second-burst false-positive generator. Real loop
  coverage lives in steer_leg's hazard gate and agent-stall (evidence
  5). If a cheap heuristic loop check is ever wanted back, it must
  compare ts-stripped identity over a window with heartbeat crumbs
  excluded — not resurrected as-is.
- "The refoundation may have changed the semantics so the probe is now
  sound." Checked the refounded path end to end: the render format
  (crumbs-db.py), the export ordering (`ts, rowid`), and the probe body
  are the same shape as diagnosed on 2026-09-02; live burst rows today
  (evidence 2) reproduce the reachable signal.
- "The 09-15 trigger could have been a genuine loop." Unrecoverable
  from the pruned DB (rowid gap), but every reconstructible firing
  traces to a burst second, the probe's construction forecloses
  cross-time hits, and three weeks of silence followed without any
  change to loop conditions — consistent with burst collisions only.
