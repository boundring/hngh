## Findings

**F1 — Recurrence is established; mechanism is not.** The alert "identical breadcrumb loop detected" fired on 2026-09-10 and again on 2026-09-15. Two firings on a ~5-day cadence is recurrence, not flapping: the trigger condition is a stable property of the system. This alone rules out "park as noise."

**F2 — No root cause is on record.** Across all prior material, neither the crumb emitter, the identity/dedup logic, nor the reason an identical loop would recur across days has been identified in code or in writing. This is the line's central gap and the reason the disposition must remain conditional.

**F3 — Two candidate defect classes, both fixable.** The recurrence pattern is consistent with exactly two mechanisms:
- **(a) Emitter defect:** hngh-automation's run/idle loop legitimately re-emits the same crumb sequence each cycle, and the detector correctly catches it. The defect is repeated work in the emitter.
- **(b) Identity defect:** crumb identity is computed from too few fields (e.g., excluding run id, timestamp, or host), so distinct runs on distinct days hash identically. The detector misfires on a degenerate comparison.

Both are defects; neither justifies parking. The only park scenario is if the repeated emission is *intentional* and the alert text is misleading — and even then the corrective action (rename/retune the alert) is a fix, not a park.
