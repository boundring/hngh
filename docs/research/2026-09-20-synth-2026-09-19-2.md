# Research Line: `patrol-20260915-journal-error-unit-not-practiced` × `ledger-sync commit race`

**Line State:** Contracting (Final)
**Date:** 2026-09-19
**Scope:** Interaction between state persistence defects in patrol journals and the ledger-sync commit race; modification of hourly ledger-sync to prevent machine-committed files from overwriting uncommitted lane-staged documentation.

## Executive Summary

The `patrol-20260915-journal-error-unit-not-practiced` defect and the `ledger-sync commit race` are not independent issues but coupled failure modes. The persistence defect (failure to durably record an error state) causes subsequent patrol cycles to treat a failed lane as fresh, triggering retries. The ledger-sync mechanism, operating on an hourly schedule with broad staging permissions (`git add -A` or equivalent), commits these retried writes over uncommitted lane-staged documentation. Because the failure was never persisted, no guard exists to flag the overwrite. This converts a scheduling overlap into silent data loss of human/agent-staged work.

The ledger-sync mechanism **can** be modified to prevent this, but only if both the commit pathspec is narrowed and the error state is propagated via the ledger itself. Fixing one without the other leaves the failure vector open.

## Findings

### F1: The Persistence Defect Enables Blind Retries
The `patrol-20260915-journal-error-unit-not-practiced` state indicates that an error unit was observed but not "practiced" (i.e., durably persisted into a form readable by the next run). Per prior material, this means the next hourly cycle re-enters the same lane with no memory of the prior failure. The retry is indistinguishable from a fresh run to the system.

*Verification Note:* This finding is based on the line's prior synthesis and the cited vault pointers (`[[sources/LES-fail-20260915-Does-the-research-lines-tsv-schema-inclu]]`). No fresh code read of the patrol journal persistence logic was performed in this transition. The specific file path for the patrol journal state handler in `hngh` or `hngh-automation` is not confirmed in prior material and requires verification before implementation.

### F2: Ledger-Sync Commits Overwrite Lane-Staged Work
The hourly ledger-sync mechanism machine-commits files on a schedule without regard for lane-staged (uncommitted) documentation in the same working tree. Per `[[concepts/hngh-lessons-current]]` and `[[sources/SRC-2026-08-24-021]]`, this is a known lesson: machine commits land on top of lane-staged work. The evidence-ledger design intent (`[[concepts/evidence-ledger]]`) relies on append-only provenance, which is violated when machine commits overwrite uncommitted staged changes.

*Verification Note:* The exact staging command in the ledger-sync script (e.g., `git add -A` vs. pathspec-limited `git add <path>`) was not located in prior material. This claim is based on the "commit race" lesson cited in vault pointers. A code read of the ledger-sync entrypoint in `hngh-automation` is required to confirm the staging behavior before implementing R1.

### F3: Composition Creates Silent Data Loss
The interaction is multiplicative:
1. Patrol fails, error unit not persisted (F1).
2. Next cycle retries write path as if fresh.
3. Ledger-sync runs, stages all changes (`git add -A` or equivalent), commits machine-side.
4. Lane-staged documentation (from the failed patrol or concurrent human/agent work) is overwritten by the machine commit.
5. No alert fires because the failure state was never recorded to flag the overwrite.

This composition means that fixing only the commit mechanism (e.g., narrowing pathspec) leaves the blind-retry problem intact. Fixing only persistence (recording error units) leaves the overwrite vector open if the retry still occurs before the guard can act. Both must be addressed simultaneously.

### F4: Ledger Authority Requires Append-Only Integrity
Per `[[concepts/evidence-ledger]]` and `[[sources/SRC-2026-08-24-021]]`, ledger authority derives from append-only provenance. Machine commits that overwrite uncommitted work violate this principle by introducing non-deterministic, history-altering changes into the ledger subtree. This undermines the trust model of the evidence ledger, making it unsuitable as a source of truth for cross-host state propagation.

## Recommendations

### R1: Narrow Ledger-Sync Commit Pathspec
**Action:** Modify the ledger-sync script to stage an explicit allowlist of paths it owns (e.g., `ledger/hosts/<hostname>/`) rather than using `git add -A` or equivalent broad staging. Machine commits must never sweep in files outside ledger-sync's owned paths.

**Rationale:** This structurally prevents machine commits from touching lane-staged documentation outside the ledger subtree. It aligns with the evidence-ledger design intent of append-only provenance within a controlled scope.

**Verification Required:** The exact staging command in the ledger-sync script must be located and modified. Prior material does not confirm the file path or current implementation. A code read of `hngh-automation` (likely `ledger_sync.sh`, `ledger_sync.py`, or similar) is required before implementation.

### R2: Path-Segregate Machine-Committed vs Lane-Staged Content
**Action:** Ensure machine-committed ledger entries live under a per-host, per-mechanism subtree (e.g., `ledger/hosts/<hostname>/`) that lane work never writes to. This makes overwrites structurally impossible rather than procedurally discouraged.

**Rationale:** Path segregation ensures that even if staging is broad, the commit content does not overlap with lane-staged paths. This aligns with the evidence-ledger design intent in `[[sources/SRC-2026-08-24-021]]` and `[[concepts/evidence-ledger]]`.

**Verification Required:** The current directory structure of ledger entries in `hngh`/`hngh-automation` must be confirmed. Prior material does not specify the exact path convention. If lane work currently writes to `ledger/`, this recommendation requires a migration plan.

### R3: Pre-Commit Guard on Dirty Lanes
**Action:** Before machine-committing, ledger-sync should check for uncommitted changes in overlapping paths and, if found, either skip the cycle (with an append-only skip entry) or commit only its own pathspec. Skipping is safer than stashing; stash/pop across an hourly boundary is its own race.

**Rationale:** This provides a runtime guard against overwrites even if path segregation (R2) is not fully implemented. The skip entry preserves the failure state in the ledger, enabling cross-host visibility.

**Verification Required:** The pre-commit hook or script logic in `hngh-automation` must be located and modified. Prior material does not confirm the existence of a pre-commit guard. Implementation requires adding new logic to the ledger-sync entrypoint.

### R4: Persist Error Units into the Ledger Itself
**Action:** Modify the patrol journal error handling to write the error unit as an append-only ledger entry, so ledger-sync propagates the failure state to other hosts rather than stranding it in a local journal. This closes the loop: the mechanism that was destroying lane work becomes the mechanism that broadcasts the failure that caused it.

**Rationale:** This fixes the persistence defect (F1) by leveraging the existing ledger-sync propagation mechanism. It ensures that the failure state is visible to other hosts and future cycles, enabling fail-closed retry semantics (R5).

**Verification Required:** The patrol journal error unit structure and its serialization format must be confirmed in `hngh`. Prior material does not specify the file path or schema for error units. Implementation requires modifying the patrol journal writer to emit ledger-compatible entries.

### R5: Fail-Closed Retry Semantics
**Action:** A patrol that reads a prior un-practiced error unit for its lane should halt or escalate rather than re-attempt the write. The 2026-09-15 LES-fail pattern (cited in `[[sources/LES-fail-20260915-Does-the-obs-2026-08-25-hngh-automation-]]`) indicates that blind retries are a known failure mode.

**Rationale:** This prevents the retry from triggering the overwrite vector (F3). If the error unit is persisted (R4), the patrol can read it and halt, avoiding the write that would be overwritten by ledger-sync.

**Verification Required:** The patrol retry logic in `hngh` must be located and modified to check for prior error units before re-attempting writes. Prior material does not confirm the file path or current retry behavior. Implementation requires adding a pre-write check to the patrol lane handler.

## Open Threads

1. **Exact File Paths Unconfirmed:** The specific file paths for the ledger-sync script, patrol journal writer, and patrol retry logic in `hngh`/`hngh-automation` are not confirmed in prior material. A code read is required before implementing R1–R5.
2. **Directory Structure Migration:** If lane work currently writes to `ledger/`, R2 requires a migration plan to segregate paths. The scope of this migration is unknown without a repository audit.
3. **Cross-Host Propagation Testing:** R4 assumes ledger-sync propagates error units to other hosts. This behavior must be verified in the `hngh` kernel repository and `hngh-automation` to ensure that append-only ledger entries are correctly synced and readable by patrol logic on remote hosts.
4. **Stash/Pop Race Mitigation:** R3 recommends skipping over stashing. The implementation of the skip entry format and its interaction with ledger-sync's commit logic must be designed to avoid introducing new races (e.g., partial commits, lock contention).
