## Findings (carried from the expanding phase, unamended)

- **F1.** "Console parity" decomposes into a five-item enumerable surface: tab lifecycle (create/close/switch/reorder), input parity (shortcuts + deterministic focus-after-close), state parity (per-tab scroll, session restore), addressability (deep-linkable tabs/articles), content parity (tab bodies render losslessly as articles). This decomposition is the line's most durable product — it converts a vague goal into a checklist.
- **F2.** The cutover cost is dominated by whether tab *state* is separable from tab *chrome*; the visual swap itself is cheap once state is pure. The gate is a property of the existing code, not of the design.
- **F3.** Winamp-style framing decomposes into three independent layers — frame *operations* (parity-bound), *draggability* (additive), *skinning* (additive) — which can ship in that order with no coupling between them.

## Recommendations (final)

### R1. Parity is a checklist artifact, not an adjective
The five-item surface from F1 is the definition of done. It should exist as a tracked artifact adjacent to `research-lines.tsv` (the prior beat proposed a `console-parity-checklist.md` in the same directory — the exact filename is a **[VERIFY]** on write, but the *location principle* — co-located with line state — is the recommendation). Items are ticked only against observed behavior of the running console. A feature the console never had is a scope decision, not a parity obligation, and cannot block the cutover.

### R2. The smallest cutover is rendering-layer-only, gated on state/chrome separability
The line's core question has a conditional answer, and this is the line's headline result:

- **If** tab state (set, active, order) is separable from chrome: the smallest cutover is a single rendering-layer swap — the same tab model drives newspaper-article frames instead of a tab strip. One step.
- **If** entangled: the smallest cutover is a forced two-step — (1) extract a pure tab model with zero visual change, ship, re-verify the R1 checklist unchanged; (2) swap chrome onto the extracted model.

The gate check is one search: find the module handling tab switching and shortcuts and determine whether it mutates DOM directly or mediates a state object. **[VERIFY]** — which repo owns the console UI (`hngh-automation` vs. `[redacted path] is itself unconfirmed. Do not begin a chrome swap before step 1's output passes R1.

### R3. Parity constrains frame *operations*, never frame *decorations*
The article-frame titlebar must expose exactly the operations the tab strip exposes per the R1 checklist — no more required, no fewer permitted. The additive layers ship after parity, in order:

- **Draggability:** pointer-driven repositioning + drag-to-front z-order. One decision: persisted (localStorage) vs. ephemeral positions. The line's recommendation is **ephemeral first** — persistence is a schema commitment, and an ephemeral layer can be upgraded to persisted without breaking anything, while the reverse migration is painful. **[VERIFY]** only that no existing code already persists window/tab geometry, which would flip the recommendation.
- **Skinning:** implement as a theme layer over CSS custom properties on the frame chrome (titlebar texture/color, border, button glyphs), so a "skin" is a data file, not code. The prior beat's intent to research actual Winamp skin formats (`.wsz`/`.wal`) for inspiration was **never verifiable from within this line** and is recorded here as unverified external interest, not a finding. Do not couple skin loading to any external format until that research actually happens.

### R4. Landing polish is out of scope for the cutover — deliberately
"Landing polish" rode along in the line title but has zero interaction with console parity. Folding it into the cutover would violate R2's minimality. Recommendation: split it into its own line if it still matters; this line closes without it.

## Answer to the line's question

**The smallest cutover that keeps console parity is a rendering-layer-only swap of tab chrome for newspaper-article frames, driven by the existing tab state model, gated on a written five-item parity checklist (R1) and on a verified state/chrome separation (R2). If the separation does not exist, the smallest cutover is a zero-visual-change state extraction followed by the same swap. Draggability, skinning, and landing polish are strictly downstream and strictly optional.**
