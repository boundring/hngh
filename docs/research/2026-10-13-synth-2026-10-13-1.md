## Recommendations (carried forward and finalized)

**R1 — Instrument first, recalibrate second.**
Add measurement at the handoff dispatch boundary in the hngh kernel: per-handoff scheduling latency (schedule-requested → execution-started), execution duration, and token consumption, persisted as structured log records so a distribution can be computed. **Caveat:** I could not verify the specific kernel file where patrol dispatch lives; locating that dispatch site is the first concrete action of this slice and should be confirmed directly in `[redacted path] before any edit.

**R2 — Land the failing tests as the deliverable, sequenced after measurement.**
Order: instrumentation (R1) → measured distribution → failing tests expressing the *target* distribution → threshold/token edit satisfying `fail-20260916-patrol-handoffs`. Tests written before measurement must assert desired bounds, never observed ones.

**R3 — Include a moment-of-action freshness test case.**
At least one failing test must cover conditions changing between scheduling and execution, asserting the patrol rechecks validity at execution time. Per the CaMeL capability-isolation lesson (`sources/SRC-2026-08-24-002`), recalibration must not widen the window in which a stale handoff retains authority.

**R4 — Prove instrumentation with the async-proof pattern.**
Per `sources/async-proof-pattern-for-long-drop-ins`, validate long-running measurement with background-job proof rather than synchronous spot checks; one-off timing runs will miss the scheduling-delay tails where handoff deaths plausibly concentrate.

**R5 — Fix beat truncation in the research-line harness.**
Beats should budget output explicitly (conclusions/recommendations first, context second) so a token-cap hit degrades gracefully. This is the same drift class as the harness observation cited in F5 and should be tracked alongside it rather than as a one-off.
