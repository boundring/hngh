### F2. rc=255 is a catch-all; the probe log must carry stderr to classify

SSH exit code 255 means "connection did not complete." It does not by itself distinguish:

- host powered off / network partition (no TCP SYN response),
- sshd not listening (RST on port 22),
- auth failure after handshake,
- firewall/iptables drop.

The prior beat identifies a **gap in the probe itself**: if the automation records only `rc=255` and not the stderr line (e.g. `ssh: connect to host … port 22: No route to host` vs `Permission denied` vs `Connection refused`), the alert is under-specified for triage. This gap is independent of whether the underlying fault was transient or persistent.

### F3. Hourly cadence and date-scoped identity create a limbo window

The facts pull ran on an hourly schedule (00:01Z, 01:01Z pattern confirmed by the two successful landings). The alert identity `deck-unreachable-2026-09-12` follows a `<scope>-<condition>-<date>` pattern. Two consequences follow from this pairing:

1. **No self-heal path for persistent faults.** If the underlying condition (host down, NIC pulled, sshd crashed) persisted past midnight, the next tick would generate a *new* identity (`deck-unreachable-2026-09-13`), not re-fire the same one. The 2026-09-12 identity is stale but never formally closed unless an explicit close/ack transition exists in the alert-emission module.
2. **No self-heal path for identity drift.** If a credential or inventory rotation on 2026-09-12 invalidated the probe identity (key rotated, host migrated, DNS shifted), the automation has no retry-with-new-identity path. The probe keeps hitting a stale address/identity and returns rc=255 every tick for the rest of the day, producing the exact observed signature: works at 01:01Z, dead for ~23 hours.

Both mechanisms produce an identical external signature (rc=255 from 02:01Z onward). Distinguishing them requires the stderr line (F2) and a check of the credential/inventory management system for a mid-day rotation event on 2026-09-12.

### F4. Per-host vs deck-wide flip is undetermined

The prior beat notes: if only one host in the deck flipped, it is a per-host fault; if all deck members flipped simultaneously at the same tick, it is a network or credential rotation event. The prior material does not record which case applied on 2026-09-12. This distinction is load-bearing for disposition (F5).

## Recommendations

**R1. Capture stderr in the probe log.** The ssh probe must record the full stderr line alongside rc=255. Without it, every future unreachable alert is under-specified for triage. This is the single highest-leverage change and is independent of the 2026-09-12 root cause.

**R2. Add an explicit close/ack transition to the alert-emission module.** Date-scoped identities (`<scope>-<condition>-<date>`) need a terminal state that is reachable without requiring the next successful probe. Otherwise, any condition persisting past midnight leaves the prior day's identity in limbo indefinitely.

**R3. Add a retry-with-new-identity path or a staleness check.** If credential/inventory rotation can invalidate the probe target mid-day, the automation should either (a) re-resolve the target from the inventory on each tick, or (b) emit a distinct alert identity for "probe target stale" vs "host unreachable" so the operator can distinguish F3 mechanism 2 from mechanism 1.

**R4. Record per-host vs deck-wide scope in the alert payload.** The alert should carry the set of affected hosts, not just the deck-level condition. This makes F4's distinction visible at triage time rather than requiring a post-hoc log scan.
