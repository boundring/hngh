## 1. Findings

### 1.1 The structural conflict

A single `hngh_wl` whitelist serves two consumers with incompatible needs:

| Consumer | What it needs the whitelist to do |
|----------|-----------------------------------|
| **Tree-skew detector** | Suppress noisy tree-rebuild events (tree-skew flapping) |
| **Artifact monitor** | Discover and audit plan-ledger state changes |

The ledger is currently placed under a whitelisted path. That placement achieves the skew detector's goal (silence) but produces the monitor's failure (invisibility). The ledger is unversioned (not in git), so there is no alternative audit trail.

### 1.2 The core tension (re-stated)

The whitelist exists because the skew detector has a false-alarm problem. The ledger is unversioned, so it cannot be tracked by version-control-based monitoring. The two consumers cannot share one whitelist without one of them losing its signal.

## 2. Recommendations

### 2.1 Recommendation 1 (primary): Split the whitelist into two namespaces

**What:** Introduce two distinct configuration sets instead of one shared `hngh_wl`:

| Namespace | Purpose | Consumer | Ledger treatment |
|-----------|---------|----------|-----------------|
| `skew_suppress` | Rate-limit / silence tree-skew flapping | Skew detector only | Ledger path lives here — flapping stays silent |
| `monitor_exclude` | Full invisibility to artifact discovery | Monitor only | Ledger path must **not** live here |

**Why this is minimal:** It requires no change to the skew detector's logic. It only adds a second lookup table and a routing decision at the whitelist entry point. The ledger's path moves from the shared set into `skew_suppress` only.

**Verification target:** Confirm that `hngh_wl` is currently consulted by both consumers. If it is only consulted by one, the "silent audit gap" does not exist and the fix is a configuration change, not a code change.

### 2.2 Recommendation 2 (fallback): Digest-only watch on whitelisted files

**What:** If namespace splitting is not feasible, add a lightweight digest tracker to the monitor that records rolling hash + size + mtime for individual files under whitelisted paths, without triggering alerting.

**Why this is a fallback:** It requires modifying the monitor's pipeline to distinguish "alert-worthy" from "record-worthy" events. Higher implementation cost than Recommendation 1.

**Verification target:** Confirm that the monitor currently operates on directory-level events rather than per-file digests. If it already tracks per-file state, this fix may be a configuration tweak.

### 2.3 Recommendation 3 (fallback): Relocate the ledger to a non-whitelisted path

**What:** Move the plan ledger out of any whitelisted directory entirely.

**Why this is a fallback of last resort:** It preserves the current single-whitelist model without code changes, but it breaks the ledger's co-location with the processes that write it, which may cause its own operational problems.
