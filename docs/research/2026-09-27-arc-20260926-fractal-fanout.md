## Findings

**F1. The line's design space is two-dimensional, and cost review is the binding constraint on both.**
The charter fixes the variables: (a) *fan-out shape* — how many questions the matrix generates per question-node row per loop pass — and (b) *confidence gates* — what threshold a generated question must clear to be accepted, escalated, or dropped, given that every gate consumes budget. **[grounded in line charter]**

**F2. The vault prior art already contains a coherent gate architecture; the line's contribution is fitting it to the question matrix, not inventing one.** **[inherited — pointers cited by the prior beat; underlying notes not opened]**
- *Long gates run async against interjections* — expensive verification should not block the interaction loop. Implication: per-question verification gates belong in the background; matrix entries are provisional until the gate resolves.
- *Outcome demotion at two consecutive failures* — a concrete, cheap confidence rule already in service: two consecutive bad executions demote the outcome. Implication: gate on execution outcomes, not generator self-report.
- *deadends.dev structured failure knowledge* — negative results as first-class rows. Implication: prune fan-out *before* generation against a deadends table; this is the strongest cost lever available because it prevents spend rather than auditing it.
- *Hngh Knowledge Base ingestion in llm-wiki* (obs-2026-08-19) — the KB is already an ingestion target, supporting question-node rows in `hngh-knowledge.db` as the typesafe substrate rather than a side store.
- *PostalForm* — a remote human-review channel; plausibly an escalation tier for high-stakes questions, though I cannot verify its current API or cost. **[unverified externally]**

**F3. What the line never established.** The prior beat announced an inspection of the KB but produced no findings before contracting. Consequently: the actual schema of question-node rows (whether confidence lives per row or per node), any existing gate implementation in the kernel repo, and any measured per-gate cost figures are all unknown. **[gap, stated as such]**

## Recommendations

- **R1. Bounded, tiered fan-out.** Small constant *k* questions per node per pass (order 1–3), modulated by node tier/confidence, with a hard per-pass budget. Uniform large fan-out is the shape least likely to survive cost review; tiering aligns spend with KB confidence. *(Design inference from the charter's framing — not empirically validated in-repo.)*
- **R2. Two-consecutive-failure demotion as the default confidence gate.** It is the cheapest precedented rule (F2) and gates on outcomes rather than self-report. Generator self-confidence alone should never gate acceptance.
- **R3. Async verification gates.** Adopt the long-gates pattern so loop cost is dominated by generation, not gating; accept provisionally, demote in the background.
- **R4. Prune-before-generate.** Consult the deadends/failure table before deriving questions from a node. Skipping known-failed derivations beats any post-hoc gate on cost.
- **R5. Write outcomes back.** Failed and unanswered questions become structured rows so the loop's cost profile tightens over time.
