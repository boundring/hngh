## Findings

### 1. Live-Fetch Proof

The backlog item treats "live-fetch proof" as a requirement that the pipeline can demonstrate, per feed, that content was fetched recently and successfully. This implies:

- **Measurable freshness metadata** must be attached to every ingested item (e.g., `last-fetched`, `content-hash`, `ttl-staleness`).
- **Staleness detection** must be surfaced as pipeline metadata so downstream consumers can act on it.
- The pipeline must distinguish between "fetched but stale" and "never fetched" as separate conditions.

**Grounding:** This is inferred from the backlog item naming and the prior art observation that in-toto is used for provenance tracking in the Hngh kernel. No specific feed-freshness schema or configuration file was identified in the repository.

### 2. Size Ceiling

The backlog item names "size ceiling" as a boundary condition. The pipeline must:

- **Enforce a per-feed byte limit at the parser boundary** — before content enters the processing pipeline.
- **Apply batch-level aggregation caps** — so a single oversized feed cannot cause unbounded memory consumption across a batch.
- **Fail fast** when a feed exceeds its size budget, rather than attempting partial ingestion.

**Grounding:** Inferred from the backlog item naming and the general memory-safety principle. No specific size-limit configuration file or parser module was identified in the hngh kernel repository.

### 3. Feed Rot + Ingest-Time Bounding

The backlog item conflates two related concerns:

- **Feed rot** — schema drift, endpoint changes, content corruption. This is a *specific degradation pattern*, not a generic ingest failure.
- **Ingest-time bounding** — every feed must have a maximum processing duration. Exceeding the budget triggers a fail-fast response.

**Grounding:** Directly from the backlog item name. No detection logic, timeout configuration, or remediation path was documented in prior art.
