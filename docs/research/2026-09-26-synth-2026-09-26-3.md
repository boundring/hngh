# Research Line Final Summary: Steer-vs-Kill Rule for Stalled Sessions

**Line state: contracting → terminal (final record).** This summary crystallizes the line's findings into a lasting record. The line remains in motion on idle hosts.

## Findings

### F1. The Loop-Recognition Failure Is a State Problem, Not a Threshold Problem

The recurring pattern of ten tree-skew candidates represents a structural failure: each stall re-opens the steer decision *de novo* with no durable record of prior evaluations. The problem is not that a numeric threshold is missing, but that the decision lacks state persistence across sessions. Without a registry, the same stall signature will be evaluated independently each time, producing the loop-recognition pattern.

### F2. Kill Is Not Irreversible When Salvage Exists

The conventional argument for "always steer first because kill is irreversible" is weakened by the existence of salvage operations. The real asymmetry is cost-boundedness, not irreversibility. Kill-and-salvage converts unbounded cost (re-steering the same candidate without deduplication) into bounded cost (extracting recoverable state with a defined maximum resource expenditure).

### F3. Threshold Absence Is Decidable — The Target Is the Procedure, Not the Number

The formalization target is the threshold-setting procedure, not the threshold itself. A self-expiring provisional rule with an explicit confirmation trigger can replace premature fixed numbers while the procedure matures.

### F4. Signature-Based Deduplication Collapses the Ten-Candidate Loop

A deterministic stall signature (hash of session_id, stall_state, stall_duration, stall_pattern) as canonical input to steer-vs-kill decisions, combined with a registry lookup before any steer execution, reduces the ten-candidate loop to at most one pass per distinct candidate.

## Recommendations

### R1. Implement a Steer Hypothesis Registry

**What:** A durable state store that records each steer decision with its stall signature, timestamp, and outcome.

**Why:** F1 establishes that the loop-recognition failure is a state problem — each stall re-opens the decision *de novo* with no durable record. The registry collapses the ten-candidate loop into at most one pass per distinct candidate.

**How:**
- Key: stall signature (hash of session state at stall point)
- Value: steer hypothesis + outcome + timestamp
- Query: "has this signature been evaluated?" → if yes, skip steer, proceed to kill-and-salvage
- Storage: persistent (not ephemeral session state), so it survives across session restarts

**Recommendation for hngh-automation:** Add a `steer_registry` module that gates steer decisions before execution. If a matching signature exists in the registry, the steer is not re-attempted — the prior outcome is treated as evidence against that hypothesis.

### R2. Adopt a Signature-Based Deduplication Protocol

**What:** Define stall signatures as the canonical input to steer-vs-kill decisions, replacing ad hoc per-session judgment.

**Why:** F1 and F2 together show that the asymmetry between steer and kill should set the default (steer at most once per distinct signature; on recurrence, kill-and-salvage). A numeric threshold cannot solve this because the problem is structural — it's about *count of distinct signatures*, not magnitude of stall.

**How:**
- Signature = deterministic hash of (session_id, stall_state, stall_duration, stall_pattern)
- Deduplication = registry lookup before any steer execution
- Fallback = if no registry entry exists, execute steer once; record outcome; on next recurrence, kill-and-salvage

**Recommendation for hngh-automation:** Define the stall signature schema in a governance document. The schema must be deterministic and reproducible so that the same stall always produces the same signature. This is the mechanism that makes the rule enforceable.

### R3. Formalize Kill-and-Salvage as a Bounded-Cost Operation

**What:** Kill is not total loss — salvage exists as a distinct operation that converts unbounded cost into bounded cost.

**Why:** F2 establishes that the usual argument for "always steer first because kill is irreversible" is weakened by the existence of salvage. The real asymmetry is cost-boundedness, not irreversibility.

**How:**
- Kill: terminate session, release resources
- Salvage: extract recoverable state, log outcome, update registry
- Bounded cost: salvage operation has a defined maximum resource expenditure (e.g., fixed CPU/time budget)
- Unbounded cost: re-steering the same candidate without registry deduplication

**Recommendation for hngh-automation:** Implement salvage as a first-class operation in the session lifecycle. The cost budget for salvage should be defined in governance parameters, not left to ad hoc judgment.

### R4. Implement a Self-Expiring Provisional Rule

**What:** The steer-vs-kill rule should be written as a conditional rule with an explicit confirmation trigger, not as a premature fixed number.

**Why:** F3 establishes that threshold absence is decidable — the formalization target is the threshold-setting procedure, not the threshold itself. A self-expiring provisional rule side-steps the premature commitment to a fixed number while the procedure matures.

**How:**
- Provisional rule: "steer at most once per distinct signature; on recurrence, kill-and-salvage"
- Confirmation trigger: explicit governance vote or automated evidence accumulation
- Self-expiring: rule expires after N confirmations or T time units, whichever comes first
- Fallback: if no confirmation, default to kill-and-salvage with registry deduplication

**Recommendation for hngh-automation:** Write the rule as a conditional with an explicit confirmation trigger. The rule should self-expire after sufficient evidence accumulation, preventing permanent commitment to a premature threshold.

## Open Threads

1. **Stall Signature Schema Design:** The exact fields and hashing algorithm for stall signatures need specification. This is the mechanism that makes the rule enforceable, but the schema has not been formally defined.

2. **Registry Persistence Layer:** The steer_registry module requires a persistence layer choice (in-memory vs. file-backed vs. database). The recommendation calls for persistent storage but the implementation choice is open.

3. **Salvage Cost Budget:** The bounded cost for salvage operations needs concrete parameterization (CPU/time budget). This should be defined in governance parameters but the specific values are not yet determined.

4. **Confirmation Trigger Mechanism:** The self-expiring provisional rule requires an explicit confirmation trigger. The mechanism for accumulation and triggering has not been specified.

5. **hngh-automation Integration:** All recommendations are directed at hngh-automation but the integration points and implementation timeline are not yet defined.
