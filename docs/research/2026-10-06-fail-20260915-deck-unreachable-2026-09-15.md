## 1. Findings

### F1 — Alert flip is real and documented
The deck facts pull transitioned from reachable to ssh probe rc=255 unreachable on 2026-09-15. This is recorded in `research-lines.tsv` and the alert log. The operator deactivated the deck integration later that same day.

### F2 — Causal structure is underdetermined by rc=255 alone
Three causal structures are possible:
- **Reactive deactivation**: probe failure precedes deactivation → host was unreachable, operator cleaned up after
- **Preparatory deactivation**: deactivation (or credential revocation) precedes first failure → alert should not have fired as actionable
- **Coincidence**: both events independent → probe failure unrelated to deactivation

**rc=255 is underdetermined**: it is a client-side OpenSSH failure (DNS, TCP refusal/timeout, host-key mismatch, or auth rejection) and cannot by itself distinguish "host gone" from "credentials revoked." This is standard OpenSSH behavior per `ssh(1)` man page; I cannot verify this against either repository from this session.

### F3 — Fix is not a real option
In all three causal structures, there is no live system left to fix. The only valid disposition is **park** with the correct reason string.

### F4 — Evidence gate is recoverable but not guaranteed
The gate requires two greps:
1. Alert-side: first rc=255 occurrence and last success for the deck probe
2. Kernel-side: integration deactivation timestamp

Capture stderr alongside the exit code and classify into a small enum (`dns`, `tcp`, `hostkey`, `auth`, `other`) at emit time. Retrofitting classification later is unreliable because stderr is usually not persisted.
