## 1. Findings

**F1 — Root cause (grounded in prior beats of this line).**
The 2026-09-14T19:00Z push was rejected non-fast-forward because `origin/main` had advanced past this session's base ref before the push reached the server. A prior push event — attributed to a same-host jcode session — had already moved the remote tip, so this session's commit chain was no longer a descendant of `origin/main`.

**F2 — Character of the failure.**
The NFF refusal is correct Git transport behavior: a non-`--force` push refuses to overwrite history it does not descend from. (This is standard `git-push` semantics as documented externally; I cite no in-repo source for it and treat it as an unverifiable-here external reference.) The refusal is a **symptom** of absent same-host serialization, not a defect in the kernel or transport layer.

**F3 — The "2nd refusal" signature.**
A second consecutive NFF on the same push indicates the retry path re-issued the push **without re-fetching/re-basing first**. Since the remote tip did not change between attempts, a second refusal is produced *by construction*. This is the single most actionable diagnostic in the incident.

**F4 — The coordination invariant (implementation-independent).**
Whatever concrete mechanism jcode uses, same-host coordination must satisfy:

> *At most one same-host session may hold push authority against a given remote ref at any instant.*

Without this invariant, NFF under concurrent same-host sessions is structurally guaranteed. The 2nd refusal is the observable signature of the invariant being violated — or of the invariant existing but not covering the retry path.

## 2. Recommendations (hngh / hngh-automation)

**R1 — Pre-push lock acquisition.** Before any push targeting `origin/main`, acquire an exclusive same-host advisory lock (`flock(2)` or `fcntl(F_SETLK)`) on a lock file co-located with the repository (e.g., under `/home/bricker/Projects/etc/hngh/.git/`) so every same-host session sees the identical path. Do not rely on PID files alone — stale-PID handling in jcode's retry/cleanup logic is unverified.

**R2 — Post-lock re-verification.** After acquiring the lock, `git fetch origin main` and confirm fast-forward eligibility locally:

```bash
git merge-base --is-ancestor origin/main HEAD
```

Push only if this succeeds. This converts a server-side NFF rejection into a locally detectable condition *before* the network round-trip, eliminating the refusal window entirely.

**R3 — NFF recovery must rebase, not blind-retry.** On NFF refusal, `git pull --rebase origin main`, then re-attempt the push **under the lock**. This is the direct fix for the observed "2nd refusal" (F3). The retry handler must be audited; if it re-issues the same push without re-fetching, the fix belongs in the retry path.

**R4 — Hold the lock across the full push window.** If jcode's idle detection triggers background pushes, the lock must be held from pre-push verification (R2) through push completion. Releasing between fetch and push reopens exactly the race this line investigated.
