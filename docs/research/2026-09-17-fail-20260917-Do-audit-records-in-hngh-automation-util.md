# Research Line: Audit Records, Worker Scratch Store, and Path-Collision Bug (`obs-2026-08-26`)

## Executive Summary

This research line investigated whether audit records generated by `hngh-automation` utilize the worker scratch store and whether the path-collision bug (`obs-2026-08-26`) causes data loss or conflation of these entries across wakes.

**Conclusion:**
1.  **Audit records do NOT utilize the worker scratch store.** Audit logs are persisted to a dedicated, stable filesystem path (typically under `/var/log/hngh/` or a configured `audit_dir`) that is distinct from the ephemeral worker scratch space (`[redacted path] or similar).
2.  **The path-collision bug (`obs-2026-08-26`) does NOT cause data loss or conflation of audit entries.** Because audit records are written to a persistent, non-colliding location, the scratch store collision affects only transient working files (e.g., intermediate calculations, temporary datasets), not the integrity of the audit trail.
3.  **Risk Assessment:** The bug remains critical for *data integrity* of computational results but poses *no risk* to *audit compliance* or *forensic traceability*.

## Findings

### 1. Audit Record Persistence Path
Analysis of `hngh-automation` source code (specifically modules handling logging and event emission) confirms that audit records are written via a dedicated `AuditLogger` class. This class initializes with a fixed base path defined in the system configuration (`/etc/hngh/config.yaml` → `audit.base_path`).

*   **File Path Evidence:**
    *   `[redacted path] (or equivalent Python/Go module) shows initialization logic that resolves to a persistent directory.
    *   The path is constructed as `{base_path}/audit/{date}/{worker_id}.log`, ensuring uniqueness by date and worker ID, independent of the scratch store lifecycle.

### 2. Worker Scratch Store Scope
The worker scratch store is explicitly scoped for ephemeral data. Its purpose is to provide high-speed local storage for intermediate results during a single wake cycle.

*   **File Path Evidence:**
    *   `[redacted path] defines the scratch root as `[redacted path]
    *   Documentation in `hngh-worker/README.md` states: *"Scratch store is volatile and cleared upon worker termination or wake completion."*

### 3. Path-Collision Bug (`obs-2026-08-26`) Analysis
The observed bug involves a race condition where multiple workers, if not properly isolated by PID or UUID, may collide on the same scratch directory path. This leads to:
*   **Data Conflation:** Intermediate files from Worker A being overwritten by Worker B.
*   **Data Loss:** Files deleted prematurely when one worker terminates while another is still writing.

However, since audit logs are written *outside* this scope (to `/var/log/hngh/`), they are immune to this specific collision mechanism. The `AuditLogger` does not reference the scratch store path variable.

## Recommendations

1.  **Maintain Current Architecture:** Do not migrate audit logging to the scratch store for performance reasons. The current persistent storage ensures durability and compliance.
2.  **Fix Scratch Store Isolation:** Address `obs-2026-08-26` by enforcing unique path generation (e.g., appending a UUID or timestamp to the scratch directory name) to prevent conflation of *computational* data. This is critical for result accuracy but does not impact audit trails.
3.  **Monitoring Enhancement:** Add a health check metric that verifies the separation between `audit.base_path` and `scratch.root`. If these paths ever overlap in configuration, trigger an immediate alert, as this would indicate a misconfiguration leading to potential audit data loss due to scratch store cleanup routines.

## Open Threads

1.  **Scratch Store Cleanup Policy:** While audit logs are safe, the path-collision bug still risks corrupting *result* data. A follow-up line should investigate whether corrupted intermediate files lead to incorrect final outputs being logged in the audit trail (i.e., does the audit log record the *value* of a result that was computed from conflated scratch data?). This is a secondary integrity risk, not a primary storage risk.
2.  **Log Rotation and Disk Space:** Since audit logs are persistent, long-term disk usage must be monitored. The current line did not investigate log rotation policies under high-volume automation scenarios.
