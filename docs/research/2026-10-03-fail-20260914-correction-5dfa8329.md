## 1. Findings (what the line established)

**F1 — Symptom signature.** A single user-level "Mark read" interaction produced a maximal state change: the entire report queue transitioned to "no unread reports." The event recurred twice against the same correction identifier (`correction-5dfa8329, x2`), which indicates either a repeated trigger of the same defect or a recurrence after an attempted fix.

**F2 — Bug-class taxonomy.** Four candidate classes were identified for an over-broad update effect:
- (a) **Missing/under-specified WHERE predicate** in the mark-read persistence update — judged most likely given the one-click → all-cleared signature.
- (b) **Shared code path with a bulk endpoint**, where a filter parameter became optional after a refactor.
- (c) **Client-side event fan-out** (one click dispatching N mark-read events) — less consistent with a single atomic queue emptying, but not excluded.
- (d) **Deploy/source skew** — fix present in source, live process still running pre-fix code until restart.

**F3 — Deploy-skew hypothesis is the most actionable.** The second clause of the line's question presupposes a restart as the presumed corrective action. This is directly falsifiable by comparing the running binary's build/commit identity against the commit containing the fix.

**F4 — Confounder identified.** A prior bad-execution episode (earlier mark-all-read, migration, or broadly retried failed write) may have pre-corrupted unread state before the visible click, per prior art `[[sources/session-budget-burn-prevents-discretionary-plan-selection]]`. This is unresolved and cannot be excluded from the evidence gathered on this line.

**F5 — What the line did NOT establish.** The line never obtained the actual handler source, the diff for correction `5dfa8329`, or post-restart process state. F2/F3 are hypotheses with a verification plan, not confirmed facts. This must be stated plainly in the lasting record: **the root cause remains unconfirmed, and the claim "fixed post-restart" is unverified.**

2. **Confirm or kill the deploy-skew hypothesis** by process inspection on the report queue's host: compare the running binary's build timestamp/commit hash against the fix commit. If the running binary predates the fix, the restart was the corrective action and the line can close on that basis. 4. **Add the regression test regardless of root cause.** "One mark-read → exactly one report cleared" is a cheap, durable guard against all four bug classes in F2 and should exist in the kernel's test suite even if the immediate incident resolves as deploy skew.
