## 1. Findings: The Actionability Contract

The feedback correction "links on the dashboard Plans page 404" is actionable because it satisfies the four gates of a root-cause investigation. The failure is not merely a broken link; it is a **semantic disagreement** between two subsystems within the `hngh` ecosystem.

### The Core Disagreement
The 404 error indicates that the **Plan Enumerator** (which generates the list of plans on the dashboard) and the **Page Renderer** (which serves the actual plan content) have diverged regarding the existence or location of a specific plan artifact.

*   **Enumerator:** Likely driven by `research-lines.tsv` **[given]**, which tracks line states (e.g., `planned`, `expanding`, `contracting`).
*   **Renderer:** A build step or server process that materializes these lines into viewable pages.
*   **The Failure:** The enumerator emits a link for Plan X; the renderer returns 404 because it either does not recognize Plan X's identifier, has not yet generated the page for Plan X, or Plan X is in a state where no page should exist.

### Why This Is Actionable (Not Just a Bug)
1.  **Reproducibility:** The failure is binary (200 vs. 404) and tied to a specific UI surface (Dashboard Plans Page). **[given]**
2.  **Isolation:** The fault lies at the *seam* between enumeration and rendering, not within either component individually. This allows for a targeted fix rather than a system-wide overhaul. **[inferred]**
3.  **Falsifiability:** The root cause can be narrowed to three mutually exclusive classes (H1, H2, H3), each with distinct diagnostic signatures. **[inferred]**

## 2. Root-Cause Hypothesis Space & Disambiguation

The 404 error decomposes into three possible root-cause classes. The "smallest fix" depends entirely on which class is active.

### H1: Slug/URL Construction Divergence
*   **Hypothesis:** The dashboard constructs `href` attributes using a different slugification rule than the page generator uses to name files. (e.g., one uses `kebab-case`, the other `snake_case`; or one includes a date prefix, the other does not).
*   **Signature:** The target file *exists* on disk but under a different name. All links of a specific class fail identically.
*   **Smallest Fix:** Unify the slugification logic into a single shared utility function used by both the enumerator and the renderer. **[inferred]**

### H2: Lifecycle-State Gating Gap
*   **Hypothesis:** Links are emitted for plans in states (e.g., `planned`) for which no page is ever rendered. The ledger (`research-lines.tsv` **[given]**) is the source of truth for the *list*, but the build process only renders pages for later states (e.g., `expanding`, `contracting`).
*   **Signature:** Target file is *absent*. The plan is in an early state. **Self-Test:** The current line `fail-20260912-sn-627926` is in state `planned` **[given]**. If the dashboard links `planned` lines to pages that only exist for later states, this line itself will 404. This is a built-in validation case.
*   **Smallest Fix:** Add a state-gate to the enumerator: only emit links for plans in states where pages are guaranteed to be rendered. Alternatively, render a "placeholder" page for early-state lines. **[inferred]**

### H3: Render Step Skipped/Clobbered
*   **Hypothesis:** The nightly cycle orchestrator skips or clobbers the render step for specific lines due to file collisions or race conditions.
*   **Signature:** Target file is *absent*, but the plan is in a state where it *should* have a page. Other plans in the same state render correctly.
*   **Smallest Fix:** Audit the nightly orchestrator for file-collision handling (see prior art: `[[sources/high-risk-file-collision-in-nightly-cycle-orchestrator]]`). Ensure atomic writes or unique temp-file strategies. **[inferred]**

### Disambiguation Test
1.  **Check State:** Is the failing plan in an early state (`planned`)? If yes, H2 is highly probable.
2.  **Check Filesystem:** Does a file exist for the plan under *any* name? If yes, H1 is probable. If no, proceed to step 3.
3.  **Check Logs:** Did the render step execute for this plan in the last nightly cycle? If it executed but failed, check for collisions (H3). If it was skipped, check state-gating logic (H2).

## 3. Recommendations: Smallest Root-Cause Fix

The "smallest" fix is defined as the change that reconciles the enumerator and renderer at a single point of failure, without introducing new complexity or refactoring unrelated components.

### Recommendation A: If H1 (Slug Divergence)
*   **Action:** Extract slugification logic into a shared module (e.g., `hngh/hngh-automation/src/slugify.js` **[unverified path]**).
*   **Verification:** Run the dashboard and confirm all links resolve to 200. Check that no other UI elements rely on the old, divergent slug format.

### Recommendation B: If H2 (State Gating)
*   **Action:** Modify the plan enumerator in `hngh/hngh-automation` to filter out plans in states where pages are not rendered. Alternatively, implement a "stub" page generator for early-state lines that returns a 200 with a "Plan in progress" message.
*   **Verification:** Confirm that `planned` lines no longer 404. Confirm that the dashboard does not emit links for states that have no corresponding render step.

### Recommendation C: If H3 (Render Failure)
*   **Action:** Audit the nightly orchestrator in `~/Projects/etc/hngh` **[given]** for file-collision handling. Implement atomic writes or unique temporary filenames during the render phase.
*   **Verification:** Run a manual render cycle for the failing plan. Confirm the file is created and served correctly.

### Rejected Symptom Patches
*   **Per-link Redirects:** Adding 301 redirects for each 404 link is rejected. This does not address the root cause and will break again as new plans are added.
*   **Hand-Editing Hrefs:** Manually correcting `href` attributes in the dashboard template is rejected. This is a maintenance burden that will scale poorly.

## 4. Open Threads

1.  **State-Page Mapping:** There is no documented mapping between plan states (`planned`, `expanding`, etc.) and page-rendering behavior. This should be codified in the repository documentation to prevent future H2-class failures. **[inferred]**
2.  **Orchestrator Robustness:** The prior art `[[sources/high-risk-file-collision-in-nightly-cycle-orchestrator]]` suggests that file collisions are a known risk. A comprehensive audit of the nightly cycle is recommended beyond this specific fix. **[given]**
3.  **Dashboard Resilience:** Consider adding client-side error handling to the dashboard that gracefully degrades when a plan link 404s (e.g., showing "Plan not yet available" instead of a broken link). This is a UX improvement, not a root-cause fix, but it improves user experience during transient failures. **[inferred]**
