# Final Structured Summary: A Steer-vs-Salvage-vs-Die Decision Rule

## Purpose of this record

This is the closing artifact for the research line. It consolidates the line's findings and recommendations into a durable form and enumerates the open threads that transfer to implementation work. The line began from two source artifacts — the `2026-08-30-steer-vs-die-threshold.md` research artifact and the interim judgment rule in `roguelike-agentic.md` — with the goal of replacing ad hoc per-session steer/kill judgment with a formal, tunable decision rule.

---

## Findings

**F1. The binary steer/die framing is incomplete; a third action exists.**
The `session-salvage` concept (created 2026-08-24) establishes that a stalled session can be decomposed: durable artifacts (diffs, notes, plans) are extracted, conversational state is discarded, and work resumes from a clean seeded context. Any decision rule that offers only *steer* or *die* forfeits value in exactly the cases where context is pathological but output is not.

**F2. Steer and die have asymmetric costs, which justifies an explicit middle branch.**
Steering preserves invested context but risks compounding a pathological stall; dying forfeits all invested context. Salvage decouples artifact retention from context retention, converting part of the sunk cost into recoverable state.

**F3. Four observable state variables suffice for a first formal rule.**
The contracted decision state is: `tokens_consumed`, `turns_since_progress`, `steer_attempts`, `salvageable_artifacts`. All four are cheap to observe and require no semantic judgment at decision time. "Progress" is defined mechanically: a state change the session intended (file write, accepted tool result, passing test). Deliberately resisting richer state was a finding of the line — over-specification before calibration data exists was flagged as the main design risk.

**F4. The rule's thresholds are parameters to be learned, not constants to be asserted.**
The steer-attempt limit (provisionally 2), the stall ceiling, and the budget ceiling cannot be derived from first principles. They must be calibrated against observed stall outcomes. This converts the research question into an instrumentation question.

**F5. Enforcement before measurement is unjustified.**
The line's consistent conclusion: deploy the rule in shadow mode first. No defensible sample-size claim was produced, because session volume in hngh-automation was never observed during this line — "enough" data was defined structurally (multiple observed outcomes per action class) rather than numerically.

---

## Recommendations (final form)

**R1. Implement a single decision function `f(state) → {steer, salvage, die}`.**
One function, one call site, one place to tune. Do not scatter the logic. *Unverified:* the actual stall-handling call site in hngh-automation or the hngh kernel was never located during this line (the kernel path was redacted in prior beats and `[redacted path] was not read). Locating it is implementation step zero.

**R2. Use the four-variable state schema and the contracted decision skeleton:**

- `salvageable_artifacts = false` ∧ `steer_attempts ≥ 2` → **die**
- `salvageable_artifacts = true` ∧ `steer_attempts ≥ 2` → **salvage**
- `steer_attempts < 2` ∧ `turns_since_progress` below stall ceiling → **steer**
- `tokens_consumed` above budget ceiling → **salvage** if artifacts exist, else **die**, regardless of steer count

**R3. Deploy in two phases:**
- *Phase 1 (shadow):* log the rule's recommendation alongside the operator's actual choice and the eventual outcome (recovered / abandoned / salvaged). No behavior change.
- *Phase 2 (calibration):* fit thresholds to the shadow log; only then consider enforcement.

**R4. Record the adoption of this rule in the decisions register.**
The vault contains `sources/SRC-2026-08-24-023` (Hngh Decisions Register); a policy change of this scope belongs there.
