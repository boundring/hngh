## 1. Scope and hard constraints

The line set out to confirm or falsify three claims about the steer-vs-die threshold mechanism described in the arc repo:

1. The threshold's supporting citations are unverified.
2. There is no telemetry emitted or collected around the steer-vs-die decision.
3. There are no confirmed integration points between the adoption gate and the hngh kernel.

Two constraints governed every transition of this line:

- **Sandbox-only repros** — per `[[sources/debug-repro-sandboxes-only]]`, no probing against live ledgers.
- **Async long gates** — per `[[sources/long-gates-run-async-against-interjections]]`, a full grep-and-trace across two repos is a long gate and must not run inline.

## 2. Findings

**F1 — The arc repository was never readable from any research session on this line.** Every transition reported the same blocker: `arc-20260926-descent-adoption-gate` could not be opened. Therefore none of the three claims were ever inspected against source. Their correct terminal status is **unverified-by-inspection**, which is categorically different from *falsified*.

**F2 — No hngh kernel file path met the confidence bar for citation.** The kernel repo at `[redacted path] was likewise not concretely inspected in a way that survived verification. Candidate search targets named in prior beats (event/trace/log/stat paths under `kernel/`) remain **existence-unconfirmed**. This record deliberately cites zero repository file paths rather than assert plausible-looking ones; fabricated paths would be a worse failure than an honest gap.

**F3 — A durable classification framework was established for when access is restored.** This is the line's substantive contribution:

- *Citations:* three-way taxonomy — (i) verifiable, (ii) externally unverifiable from the environment (not falsified), (iii) dangling or fabricated (confirmed falsification). Only class (iii) justifies the original claim's wording.
- *Telemetry:* "no telemetry" requires absence on **both** emission (kernel side) and collection (arc side). One-sided presence is a *partial integration* finding, not an absence finding.
- *Integration points:* a gate that mutates only local bookkeeping while claiming kernel-level steer-vs-die enforcement is *unconfirmed integration by construction*. Confirmation requires a traced call from the gate entry point into hngh kernel primitives (process control, signal, or scheduler interfaces).

**F4 — Motivating material is not evidence.** `[[syntheses/delegated-subagent-steering]]` motivates why steer-vs-die machinery matters; it is not evidence the machinery exists. Likewise, if threshold numbers trace back to inherited folklore consistent with `[[sources/LES-fail-20260915-If-drift-is-confirmed-in-the-scroll-beha]]`, the correct finding is "threshold is a convention, not a measurement" — a risk to flag, not a bug to report.

## 3. Recommendations (verification protocol for a session with repo access)

1. **Provenance bisect first.** For each numeric threshold, `git log -S <value>` in the arc repo and locate the introducing commit or vault note. Record whether any measurement accompanied it. This is cheap and resolves claim (1) before any code reading.
2. **Telemetry bisection, two-sided.** Search the arc repo for event consumption; search the hngh tree for emission near scheduling/lifecycle code. Classify as: full integration / one-sided (partial) / absent. Do not accept single-side absence as "no telemetry."
3. **Gate entry-point trace.** Locate the descent-adoption-gate decision point and trace its effect path. If it never reaches kernel primitives, file the finding as *unconfirmed integration*, with the trace attached.
4. **Run the above as an async long gate** on idle hosts, per the standing constraint — a two-repo grep-and-trace must not block interjections.
