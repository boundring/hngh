## Findings

**F1 — Root cause of the no-op "mark read" (hypothesis, high confidence in shape, unverified in source).**
Correction-3146c023's identity was re-routed per the 2026-09-15 plan. The dashboard report queue continued to display the report under its pre-re-route identity, while the backend mark-read mutation was keyed on the post-re-route identity. A mutation against the stale identity matched zero rows, and the UI neither inspected nor surfaced the affected-row count. The click therefore "appeared to do nothing": it was a silent zero-row update, not a failed click, a missing handler, or a rendering bug. The specific handler file in hngh-automation was not located in any beat of this line and remains unverified.

**F2 — The failure is a class, not an instance.**
Any identity re-routing that leaves stale identifiers in a client-visible queue produces this same symptom: silent zero-row mutations with no diagnostic surface. The dashboard's failure mode (no affected-row check, no error path) is what made the instance invisible. Fixing only correction-3146c023's row leaves the class live.

**F3 — Disposition closure is conditional, and the condition was never discharged on this line.**
Per the prior lesson `backlog-disposition-sweep-reduces-accepted-plans-by-half`, evidence-gated dispositions on this project have been trustworthy, so an established disposition is presumed to close its line absent a concrete contradiction. Applied here:

- The 2026-09-12 disposition closes this line **without a new fix** if it addressed the identity re-routing itself — i.e., if the re-route of correction-3146c023 *was* the disposition's resolution, in which case the no-op click is expected post-re-route behavior on a stale queue entry.
- It does **not** close the line if the disposition resolved only the report's content while leaving the stale-identity click path reachable from the dashboard queue.

No beat of this line read the disposition record or the current mark-read handler, so this distinction remains formally undischarged. The closing recommendation (R4) prices the check as cheap and makes it the line's single handoff item rather than grounds for a new fix.

## Recommendations (standing, for hngh / hngh-automation)

- **R1 (highest value, smallest change): fail loudly on zero affected rows.** Have the mark-read mutation return its affected-row count and surface a visible "report not found / identity stale" state in the dashboard queue when it is zero. This converts the entire class of re-routed-identity bugs from invisible to diagnosable. *Unverified dependency: the handler's file path in hngh-automation; locate it by searching for the mark-read route/mutation before editing.*
- **R2: reconcile on identity re-routing.** When a correction's identity is re-routed (as 3146c023 was on 2026-09-15), emit the old→new identity mapping so queued UI references can be invalidated or redirected, rather than leaving stale IDs live in the report queue.
- **R3: optimistic-then-reconciled UI.** Mark the item read immediately in the dashboard, then revert with an error toast if the mutation reports zero rows. Cheaper than blocking on the mutation and removes the "did my click register?" ambiguity even when the backend behaves correctly.
- **R4 (handoff, not new work): accept the 2026-09-12 disposition as closure after one cheap check.** The check: does the disposition record state that the identity re-routing was its resolution, and does the mark-read handler now key on the post-re-route identity? If yes, the line closes with no new fix; the residual symptom is cosmetic staleness of queue entries, covered by R2/R3 as preventive work. If no, the correct scope is still R1 (diagnosability) plus a one-line identity correction — not a new investigation.
