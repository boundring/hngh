# Journal — 2026-06-24

## Session M1.5 + M1.6 + M1.7: Model runtime + AI tool hub + AI orchestrator

**Commit**: `868de1a feat(M1.5+M1.6+M1.7): Model runtime + AI tool hub + AI orchestrator`

### What was done

#### M1.5 — Model Runtime Manager (B4)
- Runtime discovery: detects ollama (`ollama` binary), llama.cpp
  (`llama-server` / `llama.cpp`), python3 (comfyui/unsloth).
- `spawn-runtime :ollama model-spec`: checks if server is running on
  `:11434`, loads model, polls health. Returns `runtime-info` struct
  with `:starting` / `:ready` / `:failed` status.
- `spawn-runtime :llama-cpp model-spec`: subprocess spawn with the
  provided model path. Graceful failure when llama-server not on PATH.
- `spawn-runtime (:unsloth :comfyui)`: stubs that need Python venv
  setup — return `:failed` until then.
- `stop-runtime`: ollama unloads model via `keep_alive:0` (does NOT
  kill the shared ollama process), llama.cpp SIGTERM then SIGKILL.
- `health-check`: curl `http://localhost:port/api/version` with 3s
  connect / 8s max timeout.
- Subscribes to `resource.preempted` (auto-stops runtimes for preempted
  grants) and `resource.pressure` (preempts lowest-priority runtime on
  `:critical`).
- Supervisor integration: each runtime registered with `:on-failure`
  restart policy.
- 13 FiveAM tests (ollama is running on this system, so health checks
  and some spawn operations exercise the real server).

#### M1.6 — AI Tool Hub (B11)
- Tool registry: 8 default tools (opencode, claude, codex, gemini,
  cecli, anthropic-api, google-api, openai-api) with capability/cost
  metadata.
- Tool detection at init: marks each tool `available-p` based on which
  CLI / API key is available.
- `invoke`: three execution paths — agentic CLI subprocess spawn
  (opencode, claude, codex, gemini, cecli), direct API call via curl
  (anthropic-api, google-api, openai-api). API keys fetched from
  Secrets Manager, never put on the command line.
- `select-tool`: capability filter → availability filter → privacy
  filter → cost filter → prefer agentic over direct API.
- Cost tracking: append-only log at `state/plugins/ai-tool-hub/costs.lisp`
  with timestamp, tool, provider, model, tokens-in/out, cost-usd,
  task-hash, success flag.
- `kill-invocation`: SIGTERM subprocess, update status, emit
  `agent.failed` event.
- 17 FiveAM tests covering registry, selection logic, lifecycle, cost
  log, provider-API header construction. **No actual AI invocations** —
  tests are hermetic.

#### M1.7 — AI Orchestrator (B3)
- `delegate`: assemble meta-context → select tier → route to AI Tool
  Hub (cloud) or Model Runtime Manager (local) → emit
  `agent.spawned` / `agent.completed` / `agent.failed` → persist
  transcript at `agents/<id>/transcript.lisp`.
- `meta-context`: assembles three categories — system state (hardware,
  packages, config), recent activity (from event journal), KB articles
  (empty for M1).
- `handoff`: packages the output of one tool as input for another.
- `kill-agent`: stops invocation/runtime, emits `agent.failed` with
  reason.
- Policy management: per-task policy plist with `prefer-tool`,
  `prefer-tier`, `max-cost`, `max-latency`, `privacy`, `model`.
  Policies persisted to state store, load on init.
- Resource pressure handling: on `:critical`, preempt lowest-priority
  agents (LIFO heuristic).
- 16 FiveAM tests covering lifecycle, meta-context, policy
  management, delegation failure handling, handoff/kill logic.
  **No actual AI calls.**

### What was learned
- For `select-tool`, the "prefer agentic over direct API" tiebreaker
  belongs at the END of the filter chain, not in capability
  matching — otherwise cloud API providers get filtered out before
  cost is considered.
- The `agent.spawned` event payload needs both `:id` and
  `:invocation-id` because the orchestrator tracks agents by
  numeric ID while the tool hub tracks invocations by integer
  ID — sometimes they are the same value, sometimes different.
  Both keys make the mapping robust.
- Meta-context assembly is cheap if you read the event journal
  directly (already on disk), but expensive if you query the
  full event-bus subscriber list. For M1 we use the journal path
  and cap the recent-activity count at 20 events.

### Anomalies / followups discovered
- `select-tool` was being called with `(make-task-spec task)` instead
  of the raw task. This loses policy metadata. Fix: pass task +
  `&key max-cost privacy` directly.
- `agent.completed` events from the tool hub didn't include `:id`,
  only `:invocation-id`. The orchestrator looked up by `id` and
  silently dropped the update. Fix: emit both `:id` and
  `:invocation-id`, and look up by either.
- The local model-runtime spawn used `(delegate-policy-model policy)`
  as a string but `spawn-runtime` expected a plist. Fix: convert
  to `(:name model-name)` plist at the call site.
- `stop-runtimes-by-grant-id` was reimplementing stop semantics
  inline. Fix: route through `stop-runtime` with `:reason :preempted`
  so grant release is handled in one place.

These are addressed in the hardening commit (`905ea2f`) below.

## Session: Harden M1.5 + M1.6 + M1.7 orchestration handoffs

**Commit**: `905ea2f fix(M1.5+M1.6+M1.7): harden orchestration runtime handoffs`

### What was done
- **M1.5**: Added curl connect/max timeouts to health checks, model
  probe, and ollama unload. Routed preemption through
  `stop-runtime` with `:reason :preempted` so the grant release path
  is shared with explicit stop.
- **M1.6**: Emitted canonical `:id` in `agent.spawned`,
  `agent.completed`, `agent.failed` payloads alongside
  `:invocation-id`. Propagated `:result` and `:cost` on completed
  events. Direct API now uses provider-specific auth headers
  (Anthropic: `x-api-key`, Google: `x-goog-api-key`, OpenAI:
  `Authorization: Bearer`). Request payload and headers moved to
  temp files to avoid process-arg leakage (visible in `ps`).
- **M1.7**: Orchestrator tracks `backend-id` on `agent-info` so
  completion events from the tool hub can be mapped by either
  agent ID or invocation/backend ID. Policy `max-cost` and
  `privacy` now flow into `select-tool`. Local invoke passes a
  proper model-spec plist. Kill path handles agentic and local
  backends consistently.
- **Regression coverage**: added 3 unit tests — invocation-id
  completion mapping, runtime preemption delegation through
  `stop-runtime`, and provider-API header construction.
- Integration test: tightened help-flag grep to use fixed-string
  matching (`grep -Fq`) instead of regex.

### What was learned
- The orchestrator's `handle-agent-completed` handler was the
  single source of truth for completion mapping. Adding
  `find-agent-by-backend-id` lookup is a minimal change but
  unblocks all tool-hub integration paths.
- `stop-runtime :preempted` reason needs to skip the grant
  release inside `stop-runtime` (because the grant is being
  released by the preemption caller). Implemented via a `:reason`
  keyword argument to `stop-runtime`.

## Session M1.8 + M1.9 + M1.12: LLM threat detector + Hnghbeats + Knowledge base

**Commit**: `cc4afa8 feat(M1.8+M1.9+M1.12): add threat detector, hnghbeats, and knowledge base`

### What was done

#### M1.8 — LLM Threat Detector (B5)
- Plugin lifecycle: `init`, `shutdown`, `running-p`, `status`.
- Public APIs:
  - `review-plugin code manifest l1-findings &key context` — L2
    semantic review. Returns a verdict plist
    (`:pass :confidence :concerns :suggested-fixes :reasoning
    :trust-tier :reviewed-at`).
  - `review-behavior plugin &key since evidence` — L4 behaviour
    assessment. Returns an assessment plist
    (`:plugin :since :assessment :confidence :evidence-count
    :reasoning :reviewed-at`).
  - `explain plugin question` — user-facing summary combining
    latest L2 verdict + latest L4 assessment.
- Scheduler integration: `run-periodic-reviews` registered as a
  daily callback (default 86400s interval). On each tick,
  collects `threat.flag` events from L3 since
  `periodic-max-age-seconds` (default 7 days) and triggers L4
  review per plugin with evidence grouped by plugin name.
- Event subscription: `threat.flag` topic. When a flag arrives
  with a sourceable plugin name, an L4 review is triggered
  immediately with the flag as evidence.
- Persistence paths:
  - `config/plugins/llm-threat/prefs.lisp` — preferences
    (model, model-kind, model-size-mib, review-interval-seconds,
    periodic-max-age-seconds, confidence-threshold).
  - `state/plugins/llm-threat/history.lisp` — append-only
    history of all reviews.
  - `plugins/<slug>/review-verdict.lisp` — latest L2 verdict
    per plugin.
  - `state/plugin-observations/<slug>/assessments.lisp` —
    append-only L4 assessments per plugin.
- Resource manager integration: requests `:model-load` grants
  before each L2/L4 review, releases on completion.
- Event emission: `threat.review-verdict` (L2 and L4 both),
  `threat.assessment` (L4 only).
- KB integration: when an L4 assessment is `:suspicious` or
  `:malicious`, records a learned pattern into the Knowledge Base.
- 6 FiveAM tests covering lifecycle, L2 review + persistence,
  L4 review + assessment persistence, `threat.flag` event
  trigger, `explain` response, and direct invocation of
  `run-periodic-reviews`.

#### M1.9 — Hnghbeats (B6)
- Plugin lifecycle: `init`, `shutdown`, `running-p`, `status`.
- `perform-condensation :date <YYYY-MM-DD>`: deterministic
  summary of the day's events. Persists to
  `journal/hnghbeats/<date>.lisp`. Emits `hnghbeats.beat`.
- Categories in the summary: `:system-changes`, `:package-ops`,
  `:agent-activity`, `:costs`, `:threat-events`, `:user-activity`,
  `:errors`. Each category is a plist with `:count` and
  `:examples`.
- Scheduler integration: daily condensation callback at midnight
  (configurable; M1 uses 24h interval from midnight).
- Event subscription: wildcard `*.*` capped at 100 events.
- 3 FiveAM tests covering lifecycle (registers scheduler
  callback, subscribes), condensation persistence + event
  emission (with mixed event sources), deterministic no-op
  condensation when no events occurred.

#### M1.12 — Knowledge Base (B12)
- Plugin lifecycle: `initialize-knowledge-base`, `shutdown-knowledge-base`,
  `knowledge-base-ready-p`, `kb-status`.
- Article storage: `kb-write-article` with auto-slugified id.
  Articles include title, body, tags, keywords. Persisted under
  `knowledge-base/articles/<slug>.lisp`.
- Decision storage: `kb-record-decision`. Persisted under
  `knowledge-base/decisions/<slug>.lisp`. Decision plist
  includes context, outcome, rationale.
- Pattern storage: `kb-record-pattern` with category
  (`:threats` / `:optimizations` / `:workflows`).
  Persisted under
  `knowledge-base/learned-patterns/<category>/<slug>.lisp`.
- Query: `kb-query` matches text across titles + bodies +
  keywords + tags, with optional `:tags` filter. Returns
  results in deterministic order.
- Get-by-id: `kb-get-article`, `kb-get-decision`,
  `kb-get-pattern`.
- Lock-aware writes: checks for the existing
  `kb-article-<id>` lock before writing; returns NIL if
  another holder has the lock.
- 7 FiveAM tests covering lifecycle, article write/read,
  keyword + tag query, decision record, pattern record,
  lock-aware write, slug stability for degenerate inputs.

### What was learned
- Periodic L4 reviews can use the L3 `*flags*` directly without
  going through the event bus. This decouples the periodic path
  from event bus delivery timing and is testable in isolation.
- Hnghbeats' condensation is deterministic (no timestamps in the
  produced plist except the date itself), which means two Hngh
  instances computing the same day's condensation from the same
  journal produce the same plist. Useful for distributed beat
  verification later.
- The KB's slugify function needs a deterministic fallback for
  degenerate inputs (e.g., `"!!!"` → `"unknown-plugin"`),
  otherwise tests become flaky when the random number generator
  picks differently. Pre-tested in `kb-slugify-degenerate-id-stable`.

### Decisions made
- **D-018**: LLM Threat Detector stores history as append-only list,
  not a structured log file. Per-plugin history is implicit by
  joining `history.lisp` with `plugins/<slug>/review-verdict.lisp`
  via timestamp.
- **D-019**: Hnghbeats condensation emits a single `hnghbeats.beat`
  event per condensation call. Subscribers should re-condense to
  see category detail.
- **D-020**: Knowledge Base writes are best-effort. If the state
  store is unavailable or the lock is busy, write returns NIL but
  does not error. This keeps KB writes from blocking critical
  paths.

## Session M1.10: Backup Manager (B7) — Batch 5

**Commit**: pending (`feat(M1.10): Backup Manager with secrets exclusion`)

### What was done
- Implemented `src/plugins/backup-manager.lisp` (B7) — git-versions the
  `~/.hngh/` state tree, with a hermetic FiveAM test suite.
- Public API: `init`, `shutdown`, `running-p`, `status`, `commit`,
  `push-backup` (named to avoid shadowing `CL:PUSH`), `restore`, `diff`,
  `list-history`, `add-remote`, `list-remotes`, `managed-ignore-paths`.
- Behaviour:
  - Idempotent `git init` of the state tree on init.
  - Managed `.gitignore` (defaults + persisted user ignores).
  - Periodic auto-commit registered with the Scheduler; `config.changed`
    subscription refreshes `.gitignore`/remotes.
  - Events: `backup.committed`, `backup.pushed`, `backup.restored`.
  - Owned state: `config/plugins/backup-manager/{remotes,ignore}.lisp`,
    `state/plugins/backup-manager/history.lisp`.
- Wired into `src/core/main.lisp` (init after secrets-manager;
  reverse-order shutdown; state-tree dirs added), `src/packages.lisp`,
  `hngh.asd`.

### Security review (Oracle) + hardening
The primary guarantee is that secrets NEVER reach a commit (this pushes to
public remotes). Oracle reviewed and found 5 HIGH enforcement gaps — all
fixed with regression tests, no architecture change:
- **H1** — `git diff --cached --name-only` C-quotes non-ASCII paths
  (`"secrets/…"` with literal quotes), defeating the prefix check.
  Fix: `unquote-git-path` applied in `staged-files`.
- **H2** — argument injection: option-like values (`--repo=…`, `--force`)
  passed to git. Fix: `safe-git-arg-p` validation + `--` separators in
  `restore`/`push-backup`/`add-remote`.
- **H3** — TOCTOU race between the staging-guard check and the commit
  (scheduler auto-commit thread vs a user call). Fix: a `*git-lock*`
  (bordeaux-threads) mutex wrapping `commit`/`push-backup`/`restore`;
  the periodic lambda calls `commit` and does NOT double-lock.
- **H4** — `restore` clobbered the working tree with no safety net.
  Fix: auto-stash (`stash push --include-untracked`) before checkout;
  benign when nothing to stash; `:stashed` reported in the payload.
- **H5** — `restore` could extract secrets from history back to disk.
  Fix: reject restore when any target path is forbidden, before any
  stash/checkout.
- **M3** (cheap correctness) — the guard unstaged everything on a
  violation; now unstages only the violating paths (`git reset -- …`).
- Documented limitations (D-029): prior-committed secrets persist in
  history (mitigate with a future `verify-history` command); case-
  sensitive-FS assumption.

### Verification
- `make test` → **1090 FiveAM checks, 100% pass** (243 unit test functions;
  16 of them in the new backup-manager suite: 8 functional + 8 security-fix
  regression tests).
- `make integration-test` → **18/18 pass**.
- Working tree clean (tests operate only in temp dirs; no stray git artifacts).

### What was learned
- The Secrets Manager exposes no API to enumerate secret paths, so the
  Backup Manager owns a hardcoded forbidden list. Since `secrets/` is the
  only secret location in the system, this is provably complete for v0.1
  (D-028) — the dynamic `SecretPathDeclared` coordination from the design
  spec is unnecessary now.
- `git diff --cached --name-only` quoting (`core.quotePath`) is a real
  trap for any prefix-based path guard — always unquote git porcelain
  path output before matching.
- Defense-in-depth matters: `.gitignore` alone is bypassable with
  `git add -f`; the runtime staging guard is the actual enforcement, and
  it must be serialized (mutex) against the auto-commit scheduler thread.

### Decisions made
- **D-028**: Backup Manager secrets exclusion — hardcoded list +
  defense-in-depth + Oracle hardening (H1–H5).
- **D-029**: Documented Backup Manager limitations (prior-committed
  secrets; case-sensitive-FS assumption); deferred mitigations.

  packages), M1.15 (M1 integration tests — backup-to-remote flow 4.7 is
