# Journal — 2026-06-23

## Session M1.0a: Migrate test suite to FiveAM (D-013)

**Commit**: `8ebcbe4 feat(M1.0a): Migrate test suite from custom harness to FiveAM`

### What was done
- Migrated all 78 existing M0 unit tests from the custom `tests/unit/harness.lisp`
  framework to FiveAM. New harness lives in `tests/unit/packages.lisp` with
  `def-suite` / `in-suite` / `test` / `is` / `signals` / `is-true` /
  `is-equal` instead of `define-test` / `assert-true` / `assert-equal` /
  `assert-condition`.
- Centralised test fixture helpers in `tests/unit/packages.lisp`:
  `make-tmp-home`, `cleanup-tmp-home`, `fixture-path`.
- Migrated M0 component test files: `test-main`, `test-event-bus`,
  `test-state-store`, `test-plugin-host`, `test-supervisor`, `test-scheduler`.
- Added `(declaim (special ...))` declarations in `test-secrets-manager.lisp`
  and `test-ai-tool-hub.lisp` for cross-package special variables used by
  those plugins.

### What was learned
- FiveAM's `signals` is the right replacement for `assert-condition` — clearer
  intent and better failure messages.
- FiveAM's `(in-suite ...)` after `def-suite :foo :in :hngh` avoids polluting
  the top-level `*suite*` variable. FiveAM then runs the parent suite
  (`:hngh`) and discovers child suites automatically.
- The `def-suite :foo :in :hngh` form lets us run only the `:hngh` suite
  via `(fiveam:run! :hngh)` and get all tests in one go — useful for both
  `make test` and CI.

## Session M1.1 + M1.2: Procedural threat detection + Resource manager

**Commit**: `f33bbd6 feat(M1.1+M1.2): Procedural threat detection + Resource manager`

### What was done

#### M1.1 — Procedural Threat Detection (A7)
- Implemented L1 static analysis in `src/core/threat-detection.lisp`:
  manifest schema validation, capability-vs-code cross-check, dangerous
  function detection (eval, run-program, etc), pattern DB lookup,
  AI-generated review requirement. Returns `:pass | :fail | :ambiguous`
  via `l1-verdict` struct.
- Implemented L3 runtime observation in the same file: subscribes to
  `plugin.*` and `secret.*` event topics via the event bus, raises
  `threat.flag` events when behaviour violates declared capabilities
  (unauthorised subprocess, file access outside declared paths, network
  access to undeclared hosts, dbus calls to undeclared bus names,
  `secret.denied`).
- Pattern management: `add-pattern`, `list-flags`, `clear-flags`. Patterns
  persist to `state/patterns.lisp` and reload at init.
- `*patterns-lock*` and `*flags-lock*` mutexes from bordeaux-threads for
  thread-safe access.
- 19 FiveAM tests covering manifest variants, dangerous function detection,
  pattern management, runtime observation paths, lifecycle.

#### M1.2 — Resource Manager (A4)
- Hardware audit at init: `lspci` for GPU detection, `/proc/cpuinfo` for
  CPU, `/proc/meminfo` for memory. Persists `state/hardware.lisp`.
- `request-resource` for `:vram` (real arbitration), `:cpu-affinity`,
  `:memory`, `:model-load` (stubs that always succeed).
- Priority-based preemption: when VRAM is full, lower-priority preemptible
  grants are released to make room. `:preempt` lets admins force-release.
- Pressure monitoring: `:normal` / `:elevated` / `:critical` based on
  VRAM free percentage (40% / 20% thresholds). Emits
  `resource.pressure` event when level changes.
- 17 FiveAM tests covering hardware audit, request/release/preempt,
  pressure transitions, monotonic grant IDs, non-VRAM grant stubs.

### What was learned
- The `read-state` form binds *read-eval* to nil implicitly via the
  `safe-read-state` pattern. Use `*read-eval* = nil` explicitly when
  reading any untrusted .lisp file — even though state-store controls
  paths today, future plugin authors may bypass it.
- Dynamic dispatch on plugin capability categories works cleanly via
  `ecase` once you normalise the category symbol at the entry point —
  no need for an open dispatcher.
- For grant preemption, the cleanest semantic is "request-resource
  always tries to fulfil the request, pre-empting lower-priority grants
  if needed" rather than "request fails when full, caller preempts".
  Makes the API ergonomic.

## Session M1.3 + M1.4 + M1.11: Package manager + System config + Secrets manager

**Commit**: `f45c5c7 feat(M1.3+M1.4+M1.11): Package manager + System config + Secrets manager`

### What was done

#### M1.3 — Package Manager (B1)
- Read-only queries: `search` (`pacman -Ssq`), `info` (`pacman -Si/Qi`),
  `list-installed` (with `:explicit-p t` filter), `list-aur` (paru preferred
  over yay, falls back to yay, then empty list), `list-updates`
  (`checkupdates` + `paru -Qua`), `list-orphans` (`pacman -Qdtq`).
- Privileged operations route through the system daemon over dbus
  (`org.hngh.System.PackageManager.InstallPackages`). `remove-packages`
  is a stub for now (returns NIL — wired but not implemented).
- `check-breakage`: combines `pacman -Qk` (missing files) and
  `pacman -Qdtq` (orphans) into a single plist.
- Event publishing: `package.op-started`, `package.op-completed`,
  `package.op-failed`, `package.breakage-detected`.
- 15 FiveAM tests (all hitting real pacman on this CachyOS system).

#### M1.4 — System Config (B2)
- Read: direct file read for `/etc/` and `~/.config/` paths (with
  tilde expansion via the system daemon gdbus helper, fallback to
  direct read for user paths).
- Write: `/etc/` and `/usr/` paths go through
  `org.hngh.System.Files.WriteFile` dbus method. User paths write
  directly with auto parent-dir creation. Mode bits supported.
- `create-snapshot`: btrfs subvolume snapshot via
  `org.hngh.System.Btrfs.CreateSnapshot`. Snapshots tracked internally
  with IDs and persisted.
- `managed-paths` list (default: `/etc/pacman.conf`, `/etc/makepkg.conf`,
  `~/.config/hngh/`). Add/remove operations persist to state store and
  emit `config.managed-path-added` / `config.managed-path-removed` events.
- 14 FiveAM tests covering read/write round-trip, managed-path CRUD,
  graceful daemon-unavailable paths, multi-line content.

#### M1.11 — Secrets Manager (B8)
- Local vault backend (`secrets/vault.lisp`) with simple symmetric
  encryption. Backend discovery: `local-vault`, `keepassxc`,
  `onepassword-cli`, `vault-age`. Local-vault always available.
- Policy-checked access: `authorize` / `revoke` for per-plugin secret
  permission. `get-secret` checks policy before backend access.
- `get-secret` returns `(values value error-keyword)`: nil +
  `:not-authorized` for unauthorised, nil + `:backend-unavailable` for
  locked backend, value + nil for success.
- Access log: every get records plugin + secret name + timestamp +
  result + reason — but never the secret value. Logged for audit.
- Events: `secret.granted`, `secret.revoked`, `secret.accessed`,
  `secret.denied`. Threat detection L3 subscribes to `secret.denied`.
- 22 FiveAM tests covering lifecycle, policy CRUD, get success/denied,
  backend lock/unlock, access log, security (no values in log), policy
  persistence across init/shutdown cycles.

### What was learned
- For pacman query output, splitting by whitespace via a simple loop is
  easier than regex when the format is predictable (whitespace-separated
  tokens with header row to skip).
- For the secrets access log, the security guarantee is structural:
  the `access-log-entry` struct has no value slot at all. Even if
  someone prints/logs the entire struct, there's no value field to leak.
- File-based encryption for the local-vault backend is fine for M1
  threat-model (single-user, machine-local). Migration path: swap the
  backend implementation, keep the same `(get-secret :name plugin)`
  API. D-016 will formalise this.

### Decisions made
- **D-015**: `remove-packages` returns NIL until the system daemon
  exposes `RemovePackages` on dbus. We wire the call site but don't
  implement until the daemon side is added.
- **D-016**: Local-vault backend is the only fully-implemented backend
  in M1. 1Password / KeePassXC / vault-age detect presence but return
  `:not-implemented` for get/set. This is an explicit gap to fill in
  M2/v0.2.
- **D-017**: `Managed-paths` API is non-blocking. The system daemon
  WriteFile call has a 10s timeout. Longer operations should be
  backgrounded by the caller.
