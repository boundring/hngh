# Getting started

Four facts, each runnable on this machine: one kernel cycle, one
automation beat, the dashboard, and what stays operator-manual. Paths
backticked below are relative to the repository root.

## One kernel cycle

The kernel CLI is `scripts/hngh` (an SBCL launcher; usage line below is
the CLI's own). A run is bounded: it is admitted with a mission, a
role, and loadout limits - all four limits are required, nonnegative
integers, see `automation/config.env` - and it ends in exactly one
terminal state. Full command list: run `scripts/hngh` with no
arguments.

One real cycle, captured verbatim on 2026-09-14 (the `$` lines are the
commands, the `RC=` lines are their exit codes). `--store` points the
whole cycle at one scratch directory - the same per-run store pattern
`automation/lib/hngh-record.sh` uses for beat runs:

```text
$ mkdir -p /tmp/hngh-getting-started-store
$ ./scripts/hngh --store=/tmp/hngh-getting-started-store create-run "getting-started doc example" operator loadout-route-label=automation loadout-context-limit=2000 loadout-token-limit=1000 loadout-cost-limit=0 loadout-time-limit=600
accepted
run run-1 state=created role=operator loadout=automation mission=getting-started doc example
receipt kind=creation facts=identifier: run-1; timestamp: 2026-09-14T06:09:52Z
facts=created
RC=0
$ ./scripts/hngh --store=/tmp/hngh-getting-started-store close-run run-1 cancelled
accepted
run run-1 state=cancelled role=operator loadout=automation mission=getting-started doc example
receipt kind=close facts=closed-to-cancelled
facts=close-recorded
RC=0
$ ./scripts/hngh --store=/tmp/hngh-getting-started-store present run-1
run run-1 state=cancelled role=operator loadout=automation mission=getting-started doc example
RC=0
```

Two things the transcript does not show. First, without `--store` (or
`HNGH_STORE`, default `~/.hngh-automation/store` per
`automation/config.env`) the ledger is process-local: a later
invocation answers `no such run`. Second, the run id is per-store -
beat rows in `automation/STATE.md` all read `run-1` because each beat
records into its own timestamped scratch store.

## One automation beat

The live tier is a cadence continuum. A systemd timer per tier
(`automation/systemd/hngh-cadence-1m.timer`; siblings run
5m/10m/30m/hour/day/week/month) fires a oneshot service whose
`ExecStart` is `automation/jobs/cadence-tick.sh` with the tier in the
environment. One tick:

1. `automation/jobs/cadence-tick.sh` takes a per-tier flock (a tick
   that arrives while one is live is dropped, not queued).
2. It runs the drop-ins mounted at `automation/cadence/<tier>/*.sh`
   in lexical order, writing one breadcrumb row per launch and one
   `tick-done` row at the end.
3. Breadcrumbs are rows in `automation/STATE.md` with the shape
   `timestamp | job | event | detail` (written through
   `automation/lib/breadcrumbs.sh`).
4. Beats close the loop by recording a kernel run via
   `automation/lib/hngh-record.sh` into their scratch store, and
   longer agent sessions append their outcome rows to
   `automation/agent-handoffs.md`.
5. `update_dashboard` in `automation/lib/common.sh` folds the digests
   plus the last 60 breadcrumb rows into `automation/dashboard/data.json`.

One real excerpt from `automation/STATE.md` (2026-09-08; home
prefixes elided to `~`):

```text
2026-09-08T03:01:42Z | ping-hourly.sh | dashboard | data.json regenerated (2026-09-07 2300, hngh runs=567)
2026-09-08T03:01:43Z | ping-hourly.sh | hngh | recorded run-1 (create+arm+start+close-evacuated ok, store=basename(~/.hngh-automation/store/run-20260908T030142Z-2193815))
2026-09-08T03:02:00Z | cadence-tick.sh | mounted | tier 1m launching ~/Projects/etc/hngh/automation/cadence/1m/05-operator-items.sh
2026-09-08T03:02:00Z | cadence-tick.sh | mounted | tier 1m launching ~/Projects/etc/hngh/automation/cadence/1m/10-sessions-feed.sh
2026-09-08T03:02:00Z | cadence-tick.sh | tick-done | tier 1m ran 2 drop-in(s)
```

## The dashboard

`automation/dashboard-server.py` serves `automation/dashboard/` - a
`ThreadingHTTPServer` bound to `0.0.0.0` on `DASHBOARD_PORT`, default
8890 (`automation/config.env`; `automation/env.example` declares the
override), reachable on the LAN/phone. The unit is
`automation/systemd/hngh-dashboard.service`.

The only dynamic artifact is `automation/dashboard/data.json`,
regenerated by `update_dashboard` in `automation/lib/common.sh` (every
beat that summarizes also refreshes it) and by
`automation/jobs/refresh-dashboard.sh`; each regeneration writes its
own `data.json regenerated` breadcrumb row, visible in the excerpt
above.

No canonical screenshot artifact is maintained. What exists:
`automation/dashboard/shots/` holds one-off UI-verification captures
(`after-3d.png`, `story-20260914.png`, ...). For the real thing, serve
the dashboard and open `http://<host>:8890`.

## Prerequisites

Check first:

```text
cd automation && bash bootstrap.sh --check
```

`automation/bootstrap.sh --check` validates prerequisites only and
writes nothing (the checked set: python3 git curl jq flock sqlite3
sbcl). A full `bootstrap.sh` run additionally stages the repo-local
machine profile `automation/config/machine.env` from
`automation/config/machine.env.example` without ever overwriting an
existing one; `--install` installs missing pieces via the system
package manager only.

The environment contract is `automation/env.example`: key names only,
no values. The documented secret path is the 1Password service account
interface, `docs/records/2026-09-09-1password-service-account-interface.md`.

What stays operator-manual, honestly:

- the 1Password service-account grant, and placing
  `ONEPASSWORD_SERVICE_KEY` outside the repo (Plasma env file, chmod
  600, then `systemctl --user import-environment` at login - see
  `automation/env.example`);
- enabling the units under `automation/systemd/`;
- editing `automation/config/machine.env` (host identity; gitignored).

Then `cd automation && make test`. If something refuses, it fails
closed: absent prerequisites and absent keys degrade the tier, they do
not crash it.
